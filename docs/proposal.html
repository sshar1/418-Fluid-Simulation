Summary

We are going to implement a 3D fluid simulator based on Smoothed Particle Hydrodynamics (SPH) entirely in CUDA on the NVIDIA RTX 2080 GPUs in the GHC machines. Our goal is to scale the simulation to as many particles as possible, and to measure and explain the bottlenecks in neighbor search, memory access, and rendering along the way. If time allows, we will use OpenGL to render a continuous surface with raymarching.

Background

SPH

SPH (smoothed particle hydrodynamics) is a way of simulating fluids using discrete particles, each with a position and velocity. A fluid needs to maintain a constant density everywhere. The density of a given particle is defined by summing over its neighbors within radius h, weighted by a kernel W:

ρi = ∑j mj W(‖xi − xj‖, h)

There are two ways to enforce constant density. The first is explicit (weakly compressible) SPH: each particle is pushed against the gradient of the density field, from dense regions toward sparse ones, by a pressure force. The pressure that a particle feels is defined by

Pi = k(ρi − ρ0)

where ρ0 is the target density.

Explicit SPH is cheap per step, but the fluid visibly compresses unless the stiffness k is large, and a large k requires a very small timestep to stay stable, so it needs many substeps per frame.

The other way, which we will implement, is position based fluids (PBF) [1]. PBF is stable at much larger timesteps, so it needs fewer substeps per frame, but each substep costs more because it iterates. Constant density is treated as a constraint on each particle:

Ci = ρi / ρ0 − 1 = 0

Each timestep, PBF solves for position corrections that bring every Ci towards zero. A correction to one particle changes its neighbors' densities, so the constraints are coupled. So, PBF iterates until convergence. Each iteration first computes a scaling factor λi for each particle from its density error, then moves each particle by an amount that depends on its own and its neighbors' λ values:

λi = −Ci / (∑k ‖∇kCi‖² + ε)
Δxi = (1/ρ0) ∑j (λi + λj) ∇W(xi − xj, h)

where ∇kCi is how much Ci changes when particle k moves, and ε is a small constant that prevents division by zero.

The algorithm:

From a high level, the algorithm consists of the following steps for a given substep. For each frame, usually 3 substeps are run (more substeps is more stable but will reduce frame rate). We will have to experiment with implementation, but this is our initial idea:

  1. For each particle, apply gravity (v += gΔt) and predict its position, x* = x + vΔt.
  2. Build the grid data for the particles from their predicted positions (i.e. get the grid location of each x*).
  3. Create a histogram of particle counts in each grid cell location, do a scan, and insert each particle into the correct spot using the scan, essentially doing a parallel sort.
  4. For each particle, do a neighborhood search only within the 27 surrounding cells of this particle's cell. Compute the density using this. The neighbors found here are kept fixed for the rest of the substep, even though particles move during the PBF iterations.
  5. If using the first method for calculating pressure, simply plug in the numbers to get pressure and then move each particle to finish the algorithm. If using PBF, repeat:
    1. For each particle, compute ρi and λi.
    2. For each particle, compute Δxi.
    3. For each particle, set x* += Δx.
    4. Check convergence. If the max density error is small enough, stop iterating; otherwise, go back to step 5.1.
  6. For each particle, compute its velocity v = (x* − x)/Δt, apply viscosity, and set x = x*.

The order that particles apply their corrections within an iteration matters:

  • Jacobi: Every particle computes its corrections from values at the start of the iteration, and all particles update together. Every particle is independent within an iteration, so all particles can update in parallel. Convergence can be slower since a correction travels only one neighbor-distance per iteration.
  • Gauss-Seidel: Particles update one at a time, using the latest values of their neighbors, including ones updated in this iteration. It is harder to parallelize because of this dependency.

Parallelism

The parallelism lies in every "for each particle" statement. Additionally, the neighborhood search will benefit the most from parallelism as we can quickly make a neighborhood per particle and only search within each particle's neighborhood. Gauss-Seidel will also massively be improved with parallelism since it typically has many dependencies while waiting for neighboring particles to finish computing.

Rendering

To render for visual debugging we will use CUDA-OpenGL interop. We may expand the renderer to render a fluid volume if time permits.

The Challenge

The first challenge lies in concerns with neighborhood size. 27 cells cover 27h³, but the search sphere is 4.2h³. Smaller cells can be used, like cells of size h/2 means 125 cells covering 15.6h³, which is fewer neighbors to check but more cell lookups.

We must also consider how often to update the grid. For a correct algorithm, we need to rebuild the neighborhood table on every substep, but particles don't move much in a single substep, so this can waste work. We will experiment with:

  • (a) Full rebuild every substep.
  • (b) Sort indices every substep but physically reorder only every k substeps, since locality degrades slowly.
  • (c) Pad the cells to h + 2d and rebuild only every k substeps, where d is the maximum displacement between rebuilds. This is correct as long as no particle moves more than d. The same padding argument covers the PBF iterations within a substep, where particles move but the neighbors found at the start of the substep are kept fixed.

Because neighbors stay fixed across a substep's iterations, we can also choose between re-traversing the 27 cells in every iteration, which repeats the wasted candidate checks each time, and building an explicit neighbor list per particle once per substep (about 256 bytes per particle), which every iteration then reuses. Which is faster depends on how many iterations reuse the lists.

Divergence will also be a concern. Interior particles have many neighbors while particles at the surface or in a splash have few. Some alternatives may be putting particles in shared memory and parallelizing over cells rather than particles.

For non-PBF SPH, the main dependency is in the step where we calculate pressures. We first need to know every particle's density before we calculate its pressure. Furthermore, viscosity will read neighbor velocities while updating its own, so it needs separate input and output buffers to avoid a race.

Jacobi gives full parallelism but needs more iterations. Gauss-Seidel converges in fewer iterations but has less parallelism per pass. We will have to measure time to reach a target density error.

When implementing Gauss-Seidel iteration, we will have to use graph coloring so that direct neighbors never affect each other. We plan on using 8 colors between cells which is sufficient for separating neighbors in a 3D grid. However, within a cell, we will still do a sequential Gauss-Seidel loop. We will have to place barriers between color updates finishing. Lastly, we may have to do a global convergence check using some global reduction.

In terms of locality, particles near each other in space are not necessarily near each other in memory unless data is reordered. So, we may experiment with changing the ordering of particles in memory.

In terms of communication vs computation, for each candidate neighbor, we do very few computation, meaning our program will likely become memory-bound.

Gauss-Seidel may need many kernel launches (one per color), so launch overhead could hurt performance. For checking convergence, the CPU may have to decide, which will cause some slowdown on performance.

Goals and Deliverables

Plan to achieve

  1. An explicit (weakly compressible) SPH simulation in CUDA that behaves stably and plausibly in scenarios such as a dam break and a sloshing tank.
  2. A sort-based uniform-grid neighbor search: a counting sort built from an atomic histogram, an exclusive scan, and a scatter, with particle data physically reordered by cell. We will compare reordering every substep against reordering every k substeps.
  3. PBF with a parallel Jacobi solver.
  4. PBF with a parallel Gauss-Seidel solver using 8-color cell coloring.
  5. A multithreaded OpenMP CPU implementation of explicit SPH as a baseline.
  6. Performance target: at least 60 fps (since that would make this real-time) at 500k particles for both explicit SPH and PBF, and at least a 10× speedup over the OpenMP CPU implementation on the same machine.
  7. A thorough analysis: time to reach a target density error (e.g., max error below 1%) for Jacobi versus Gauss-Seidel; simulated seconds per wall-clock second for explicit SPH versus PBF; per-stage time breakdowns across particle counts; and achieved versus peak memory bandwidth for the main kernels.

Hope to achieve (likely not all, only 1-3)

  • 1M particles at interactive frame rates (at least 30 fps).
  • Per-particle parallel graph coloring (e.g., Jones–Plassmann [6]), recomputed every substep, compared against cell coloring.
  • Keeping the iteration loop and convergence check entirely on the GPU (a persistent kernel with cooperative-groups grid synchronization) to avoid a CPU round trip per iteration.
  • Alternative grid strategies: padded cells rebuilt every k substeps, explicit neighbor lists versus re-traversing the grid, and cells of size h/2.
  • Foam, spray, and bubble particles [7]. Each fluid particle may spawn a variable number of short-lived secondary particles per frame, which requires dynamic allocation on the GPU via atomic append buffers or scan-based stream compaction; we would compare both.
  • Rendering a continuous fluid surface in OpenGL.

If work goes more slowly

We will cut scope in this order. First, drop the Gauss-Seidel solver and compare explicit SPH against Jacobi PBF. If PBF itself is delayed, focus on explicit SPH and the grid experiments (reordering frequency and neighbor lists). In either case, our committed particle count would drop to 250k.

Poster session demo

We plan to show a demo of a pre-recorded scene: a tank of water that moves around, showing how the water responds accordingly. Since this will run on the GHC machines, we will have to pre-render multiple scenes and composite them at the same frame rate the gates machine was running at.

Questions our analysis will answer

  • Where does frame time go (sorting, each neighbor pass, convergence checks), and how does the breakdown change with particle count?
  • Does Gauss-Seidel's faster convergence outweigh its reduced parallelism, extra barriers, and worse locality compared with Jacobi, measured as time to reach a target density error?
  • Is PBF faster than explicit SPH per simulated second at the same level of compression?
  • How close do our kernels get to the GPU's memory bandwidth limit, and what prevents them from getting closer?
  • How much does physically reordering particle data improve achieved bandwidth and cache hit rates compared with index indirection?
  • How much do divergence and load imbalance from uneven neighbor counts cost, and do alternative work assignments (e.g., per-cell instead of per-particle) reduce it?

Platform Choice

SPH is a natural fit for a GPU. Every stage performs the same computation independently for each of hundreds of thousands of particles, which maps directly onto CUDA threads, and the workload is memory-bandwidth bound, so it benefits from the GPU's much higher memory bandwidth compared to the CPU. We chose CUDA rather than a higher-level framework because the optimizations we want to study require explicit control over thread-block organization, shared memory, atomics, and warp-level primitives, and because Nsight lets us measure the effect of each decision precisely. Doing the rendering on the same GPU with CUDA–OpenGL interop means simulated particle data never leaves the GPU, avoiding a per-frame transfer that would limit frame rate. Finally, the GHC machines' CPUs provide a fair multicore baseline on identical hardware.
